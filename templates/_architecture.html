A day in the life of the pipeline

Typical weekday. The morning run takes about 25 to 30 minutes end to end; nobody touches a keyboard.

  1. 5:30
    The database wakes up GitHubcron.schedule → net.http_post → workflow_dispatch

    A Postgres timer calls the GitHub API with a token stored in Supabase Vault. GitHub's own scheduler skipped runs for this repo, so the database is the clock.

  2. 5:31
    IngestRSS × {{ n_podcasts }} → new episodes → audio

    Each show's feed is read; anything new since the last run is queued with its audio file.

  3. 5:33
    Transcribe and summarizeGemini → Pydantic schema → JSON

    Audio becomes a transcript, then a structured study sheet: key points, numbers, lesson, opinions, glossary, tickers. Every answer must match a typed schema.

  4. 5:45
    Verify before anything shipschecks.py: numbers · dates · tickers · quotes

    Every number and date in a summary must appear in the transcript; tickers must exist on the exchange list; flagged fields go through a repair pass or are cut.

  5. 5:50
    Top stories, forecasts, audio{{ n_feeds }} newsrooms · round-robin · Kokoro

    Headlines from six desks are balanced so no single feed dominates; forecasts are logged only if the quote is in the transcript; the briefing is spoken by a local voice model.

  6. 5:58
    Build and publishJinja → site/ → git commit → Pages

    The whole site is rebuilt as static HTML and pushed. Phones pick it up on next open.

  7. 9:32 →
    Every 15 minutes, market hoursYahoo → prices → fill_orders() · settle()

    Quotes land in Postgres; SQL functions fill pending paper trades and settle the day's calls. The NYSE calendar (holidays, early closes) decides when to skip.

  8. 3:45
    TrendBot tradesStockTrendAnalyzer · 100-point checklist

    A robot player scores 61 stocks on trend, momentum and volume and trades with the same rules as everyone else.

  9. 4:25
    After the closeafter_close(): ranges · Sharpe · drawdown

    The 90% range game is scored and every portfolio gets a daily snapshot for risk stats and the 1W/1M charts.

Design decisions

The interesting part of any system is the trade-offs. Here are the ones that shaped this one.

The AI is never trusted with a number

Problem. Language models invent figures, misspell names and turn questions into "forecasts".

Decision. Deterministic checks after every generation: numbers and dates must occur in the source, tickers must be listed, quotes must match the transcript (exact or 85%+ fuzzy), names are corrected against newsroom spellings.

Trade-off. Some true facts get cut when the transcript phrases them differently. We accept losing a sentence over publishing a wrong one.

A database as the clock

Problem. GitHub's built-in schedule silently skipped runs for this repo.

Decision. pg_cron in Supabase fires on time and calls GitHub's API through pg_net, with the token encrypted in Vault. The jobs themselves check the NYSE calendar.

Trade-off. One more moving part, and a renamed repo means updating the SQL (it happened; migration 020).

Game rules live in Postgres, not the browser

Problem. Anything in front-end JavaScript can be edited by a player.

Decision. Orders, fills, rewards and scoring are security definer SQL functions; tables are locked down with {{ arch.n_policies }} row-level security policies, so a user can only read or write their own rows.

Trade-off. Logic is harder to iterate on than JS, so every change ships as a reviewed migration.

Static-first delivery

Problem. A free project can't pay for servers, and servers are what fall over.

Decision. Everything that's the same for every reader is pre-rendered HTML on GitHub Pages; only personal data (portfolio, streaks, friends) comes from Supabase at runtime. The mobile apps are Capacitor shells over the same site.

Trade-off. Content updates need a rebuild, which is why the pipeline ends in a git commit.

Route each job to the right model

Problem. Free-tier models differ: some are fast, some are smarter, some are often overloaded (503).

Decision. Each job has its own ordered fallback chain and hard timeouts (table below), benchmarked per task, with a local model as a last resort for offline runs.

Trade-off. Output style varies slightly when a fallback answers; schemas keep the shape identical.

Measure skill, not luck

Problem. A leaderboard of returns rewards whoever took the biggest risk.

Decision. Every trade is mirrored into the S&P 500 at the same moment (alpha), portfolios get Sharpe ratio and max drawdown from daily snapshots, and forecasts are ranked by a Brier-style skill score.

Trade-off. These need history, so the fair boards fill in over weeks, not days.
